# 技術リファレンス

アプリケーションサーバー の公開インターフェースと運用規則を説明します。

## インターフェース

### ドキュメントの閲覧

| メソッド | パス                                    | 結果                                               |
| -------- | --------------------------------------- | -------------------------------------------------- |
| GET      | `/api/v1/docs`                          | ドキュメント一式とそのバージョンの一覧を返します。 |
| GET      | `/api/v1/docs/:version/:slug`           | 選択したバージョンの概要を読みます。               |
| GET      | `/api/v1/docs/:version/:slug/usage`     | 同じバージョンの使用例を読みます。                 |
| GET      | `/api/v1/docs/:version/:slug/technical` | 同じバージョンの技術情報を読みます。               |

`langs` は言語の優先順位で、最後の代替言語は英語です。一覧には `slug`、`title`、`group`、`version`、`versions`、`sourceName`、`views` が含まれます。

`langs` は一覧の見出しと本文に使う、優先順の言語をコンマで区切った指定です。地域付きの指定は次の候補の前に基本言語を試し、英語も必須の代替として保持します。指定したコンポーネント版の情報・使い方・技術に同じ選択を適用します。

## 設定

### ドキュメントの閲覧

`COGNIS_DOCS_ARCHIVE_DIR` で保存先を指定します。指定がなければ `COGNIS_CLI_TOKEN_PATH` と同じディレクトリ、または利用者のホームの `.cognis/docs-archive` に保存します。プロセスには保存先への書き込み権限が必要です。

## 動作

### 文書の差分

文書の差分により、モジュールはユーザーが新版に対応する前に、二つの変更不可能な文書バージョン間の違いを説明できます。

### Markdown 比較ビュー

ブラウザーの `ui:documentDiff` Capability が提供する `renderMarkdownDocumentDiff(diff)` を使用すると、変更後の文書全体を Host の Markdown Renderer で描画できます。変更されていない内容は通常の文書表示を維持し、追加、置換、削除には緑、オレンジ、赤の Overlay と概要バーのナビゲーションが適用されます。 Renderer は比較内容全体を 1 回の Markdown 処理で描画するため、変更行をまたぐ Fenced Code Block、リスト、引用などの構造が維持されます。

### ドキュメントの閲覧

三つの表示と利用できる翻訳を、コンポーネントのバージョンに対応する一つの `bundle.json` に一括で保存します。完全な一式だけを一覧に表示します。インストール済みの版を再度読むと一式を更新し、他の公開済みの完全な版も参照できます。

データベース入力は DB ゲートウェイの公開された構造化契約 `ensureTable` と `executeCommand` を使用します。ストアの生成と変更不可能なストアのメソッドには明示的な TypeScript 契約があり、特定のデータベースドライバーには依存しません。

共通の動作: [TFA](/docs/gateways/tfa/technical).

無関係な設定の保存ではTFAポリシーを適用しません。TFA読み取りケイパビリティがある場合、システムの読み取りとTFA項目を省略した保存では、その現在のポリシーを使用します。読み取り失敗時は強制設定が無効と表示せず、エラーを返します。この任意のケイパビリティがない場合、保存された設定は古い可能性のあるコピーにすぎません。明示的なポリシー変更には引き続き担当コンポーネントのケイパビリティが必要です。

アカウント認証ではセッション用認証情報のみを受け入れます。混合リソースルートは `share:getGuestClaims(request)` を明示的に取得し、リソースと操作の権限を検証します。ゲスト認証が無効または利用できない場合、通常のアカウント認証だけを試み、ゲストのクレームでアカウント権限を付与しません。ハンドラー内で完全な認証を行うモジュールルートは外側のアカウントロールメタデータを省略し、管理ルートは維持します。描画に必要なプロバイダーとアプリルートの取得だけが、有効なゲスト認証と既存のロール表示条件を利用します。キャッシュしない識別エンドポイントは、検証済みの主体、ロール、プロバイダー、目的、設定状態だけを返します。

`await ctx.getCapability("share:getGuestClaims")(request)`

`Promise<{ sub: string; role: "user"; providerId: string; purpose: "share"; setupPending: false } | null>`

ドキュメントは対応するソースディレクトリの公開マニフェストを読みます。マニフェストの UUID がグループと一致し、正規化されたパスが所有元の範囲内にある必要があります。返されるのは id、name、ui.stringsBaseUrl、検証済みバージョンと並べ替えた公開言語ファイルの SHA-256 情報から生成する ui.stringsRevision だけです。設定、認証情報、実行状態、管理用カタログの情報は含みません。追加認証や管理用エンドポイントは不要です。

/static/reuse/presentation.js の共通エクスポート localizeModulePresentation をモジュール画面とドキュメントで使います。既存の名前キーとカタログ URL を使用し、キーを推測しません。優先言語の値が空または存在しない場合は英語を使います。英語の値も空または存在しない場合、キーや代替ラベルを表示せず missing_translation で描画に失敗します。

アーカイブだけに残る文書にも、所有元のマニフェストがある間は現在の表示メタデータを使います。メタデータがなければ従来の識別子を表示し、文書、バージョン、グループは引き続き利用できます。モジュールを削除しても古い翻訳名を作ったり保持したりしません。

ドキュメントのガイドは引き続きナビゲーション、現在の文書、バージョンリンクを強調します。ナビゲーションの手順では表示名によるグループを説明します。展開状態は安定したグループ ID で保持されます。翻訳の読み込み中にページ表示を中止した場合、メニューは公開されません。

言語カタログの URL は /static/modules/{id}/ 配下の正規パスで、空でない公開パス要素だけを使用します。ディレクトリ移動、クエリ、フラグメント、外部オリジンは許可しません。文字列以外の URL や不正な記述子は翻訳前に拒否します。URL を宣言していないインストール済みマニフェストは既存の /static/modules/{id}/languages を使用し、ホストはモジュール初期化前でも UUID が所有する UI ディレクトリに解決します。

任意のマニフェスト JSON、データ形状、言語記述子が使用できない場合は省略し、グループ識別子と安全な理由を構造化ログに記録します。他の有効な文書は元の識別子で利用できます。予期しないファイルシステムのエラーは引き続き伝播します。このメタデータ処理は宣言済み翻訳キーの欠落を抑制しません。

バージョン情報は明示的なカタログにも標準のカタログにも適用され、モジュール更新後の次回表示時に翻訳名が更新されます。ページと全体検索は保存済みの言語優先順位と異なる場合でも現在の表示言語を使います。バックグラウンド検索は設定を書き換えません。

同じソフトウェアバージョンでも公開言語ファイルのハッシュが変わればコンテンツのリビジョンも変わります。インストール状態を公開せず、別のタブなどで行った更新後に名前を更新できます。宣言されていない言語ファイルの変更には通常のモジュールライフサイクルによるキャッシュ無効化が必要です。

公開されたプレリリースのバージョン識別子は、アーカイブのみの文書を含め、表示リビジョンとして有効です。空白や非ラテン文字を名前に含む無関係な公開アセットは、言語の検証やダイジェストに影響しません。

正常に返されたフロー値には、期待するフロー ID、データオブジェクト、取得したものと同一の結果マップが必要です。完了結果が欠落または不正な場合は、所有者の証明があっても不明のままです。完了の検証はフローの Promise の拒否と分離しており、ローカルな結果処理の失敗を後処理の失敗とみなしません。

### 確認済み、拒否、不明

操作の所有者が確認した拒否は、元の 400、403、404 のステータスと 元の安全な `error.code` と `error.message`、`data.outcome: rejected`、`data.deleted: false` を返します。これにより拒否と部分的に実行された操作を区別します。削除フロー開始前の検査による拒否は、従来の応答契約を維持します。

構造が正しい完了結果が返され、結び付け済みの証明リーダーが証明を利用不能と判断した場合は、HTTP 503 と既存の安全な `error.code`、`error.message`（どちらも `account_policy_unavailable`）を保持し、`data.deleted: null` と `data.outcome: unknown` を追加します。ポリシーや認可証明の利用不能、結果証明の欠落、不正、失効を含みます。区別できないこれらの状態はアカウント削除の前後どちらでも起こり得るため、503 を拒否や `deleted: false` の根拠にはしません。

証明が確認できないフロー例外、欠落または不正な完了結果、永続化証明のアカウントや操作の不一致は、HTTP 500、`error.code: user_deletion_outcome_unknown` と同じ null/unknown データを返します。完了したフローでも、一致する正式な証明がなければ成功を確認できません。

応答が失われたり読めなかったりすると、サーバーで削除が確定していても呼び出し側の結果は不明です。次の操作を決める前にアカウントと運用記録を確認してください。後の照会でアカウントが見つからないだけでは、どのリクエストが削除したかは証明できません。自動再試行や後処理の再実行は行いません。

### 証明と復旧の境界

API は登録済み認可フックより前の呼び出し専用ハンドラーで、実際の呼び出しの結果マップの同一性を取得します。既存フックは順序を維持して通常どおり実行されます。事前に束縛され、現在も有効な `auth:deprovisionOutcome` リーダーだけが、元の入力と正確な呼び出し同一性に対応する結果を確認できます。公開されたステージ値、結果のコピー、別のリクエストの証明は削除の根拠になりません。

通常の 200 応答はフローの復帰後に削除を確認しますが、依存コンポーネントの全作業の完了を新たに保証しません。一致する永続化証明があるフローの例外は、削除を確認しつつ後処理が未完了であることを報告します。API は安全な失敗分類を記録し、構造化応答を一度だけ書き込み、元の例外を再送出します。そのため既存のコンポーネント復旧境界は帰属と集計を維持します。内部の例外詳細は返しません。

### 互換性

通常の成功ペイロードとフロー開始前の拒否形式は変わりません。所有者が確認した 400/403/404 の拒否は安全なエラー項目を保持し、`data.outcome: rejected` を追加します。有効な完了結果で証明が利用不能の場合は、既存の 503 エラー項目を保持して不明な結果を追加します。部分的または不明な結果を伴うフロー例外と不正な完了結果には HTTP 500 を使います。利用側はステータスだけから削除を推測せず、明示された結果を確認する必要があります。

## セキュリティ

ドキュメントのエンドポイントは読み取り専用の情報を公開します。認証情報や個人のアカウント情報を含めないでください。文書の比較機能を使う別のルートは、それぞれ認証と文書のアクセス権を確認します。

## リファレンス

### 技術仕様

両方のハッシュがストアの名前空間に存在し、同じ文書スラッグに属している必要があります。結果には比較元と比較先のハッシュ、共通スラッグ、および `unchanged`、`added`、`removed`、`changed` に分類された順序付きの行が含まれます。変更された項目には以前の文章と置換後の文章の両方が含まれます。

ブラウザレンダラーは動的な文章をエスケープし、追加を緑、変更をオレンジ、削除を赤で表示します。
