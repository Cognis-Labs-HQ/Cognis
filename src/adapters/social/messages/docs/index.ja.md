# Messages ブラウザークライアント

新しいグループルームは、鍵の生成とすべてのメンバーの登録を完了してから連携元を確保します。初期化や関連付けに失敗すると未完成のルームを削除し、削除の失敗もログに記録して呼び出し元に伝えます。既存のルームと連携元の排他的な関連付けは維持します。

Messages ブラウザークライアントは、Social Messages アダプター所有の認証済み API 契約を通じて、モジュールによるルームメッセージ一覧、プライベートルーム作成、メッセージ送信を可能にします。

## 使用例

`uiCtx` をインポートして `social:messagesUiClient` を要求し、ブラウザーコードから `listRoomMessages(roomId, options)`、`openPrivateRoom(payload, options)`、`sendRoomMessage(roomId, payload)` を呼び出します。

## 技術仕様

クライアントは元の `Response` を返し、状態とペイロードの処理を呼び出し側に委ねます。ルーム ID を URI エンコードし、ルート知識を所有アダプター内に保持し、任意のアクセストークンとアクセス拒否通知の抑止を転送し、書き込みを JSON で送信します。Social ゲートウェイと Messages アダプターが有効な間だけ利用できます。

公開機能 `social:messages:deleteChatroom` はルーム ID と実行者のアカウント ID を受け取ります。実行者がルームの作成者、または唯一残った参加者である場合に、ルームとその依存レコードを完全に削除します。

アダプターは `social:messages:resolveRoomMembership` も公開します。ルーム ID と要求元アカウント ID を受け取り、アクティブなルームメンバーだけを認可して、アクティブメンバーのアカウント ID を返します。プロバイダーは Messages の永続化層を直接読み取らず、この境界を使用します。

「新しいルーム」選択画面は、Jitsi Meet などのユーザー専用検索と同じく、共通検索ポップアップの `category: "user"` と `typeFilter: "user"` パラメーターを使用し、会話の作成候補をユーザー結果だけに限定します。

着信はスレッドヘッダーの直下に提供アクションバーとして表示され、左側にラベル、右側にプロバイダー所有の応答・拒否 SVG アクションを配置します。過去の通話イベントは操作プロンプトではなく通常のタイムライン記録として残ります。

このアダプターは、ルーム単位のタイムラインイベントを記録するコンポーネント向けに、汎用 Capability `social:messages:appendRoomEvent` を公開します。ペイロードには中立的なイベントメタデータだけを保存し、ドメイン固有のイベント名とフィールドは所有コンポーネントが管理します。ブラウザ Flow `messages:formatRoomEvent` により、各コンポーネントは Messages に文字列や描画規則を追加せず、ローカライズ済みの表示を提供できます。

### 資源ごとの会話

`social:messages:resolveGroupChatUrl` は `usernames` と任意の `title`、`createdByAccountId`、`allowSingleMember`、`reuseExisting`、`roomId` を受け取ります。既定では同一メンバーのグループを再利用します。`reuseExisting: false` は独立した会話を作り、保存済み `roomId` はメンバー変更後も保持し、削除済みなら置き換えます。新規ルームには鍵とメンバーを設定し、再利用ルームの名前は維持します。ミーティングなどの独立資源に使える中立的契約です。

## 連携元の排他的な参照設定

`social:messages:sourceBinding` は `{roomId, actorAccountId, sourceType, sourceId}` を受け取る `bind` と `release` を提供します。グループ解決は `source: {sourceType, sourceId}` も受け取ります。権限のあるルームメンバーは未設定のルームを参照元に関連付けられます。別の参照元には `source_conflict` を返し、既存の設定を上書きしません。同じ参照元からの再設定は冪等です。条件付き更新で同時リクエストを制御し、解除は一致する参照元だけを対象とします。グループ解決と参照設定は登録済みのctxフローで実行します。

ブラウザープロバイダーはスコープ付きctxから `ui:scopedActions` を取得します。`(ctx, moduleId, actions)` を渡すと、各操作の実行可能なフローを登録し、公開用の操作関数を返します。管理画面の取得・更新にこれらの関数を使用します。ホストがフローの破棄を管理し、破棄後の古い関数は実行を拒否します。管理者権限は有効なアカウントの現在の役割から検証し、呼び出し側が渡した役割には依存しません。

## オフラインのソーシャル変更

Profile と Messages のプロバイダーは ctx 経由で有効期間に対応した HTTP 操作を登録します。検証済みのタブでは、読み込み済みのプロフィール・投稿・ルーム一覧・暗号化された履歴を利用できます。プロフィール文、在席状態、フォロー・ブロック状態、バナー配置、投稿の作成・削除、既存ルームの暗号化メッセージ、リアクションの最終状態、既読通知をアカウント別に送信待ちとして保存します。後のオンライン編集も同じ所有者の保留項目を待ちます。準備中やキューの待機中にアカウントやセッションが変わると操作を中止します。メッセージと投稿は安定した `operationId` UUID を使い、内容の相違や他のアカウントからの再送を拒否します。メッセージの再送で通知は重複しません。既読通知は元の閲覧時刻を維持します。

チャットは保存前に暗号化し、平文・ルームキー・認証情報をキューに追加しません。プロフィール文と投稿内容は現在のアカウントのブラウザーストレージに保存します。最大 350,000 バイトのアバター・バナーは既存の 1 MB・1,000 件・7 日間のキューを共有します。大きな画像には接続が必要です。容量不足では翻訳済みのエラーを表示し、メッセージと投稿の下書きは永続保存に成功した後にのみ消去します。制限は各コンポーネント単位ではなくキュー全体に適用します。

変更はサーバー確認まで保留します。メッセージには送信待ち状態を表示し、プロフィール・投稿・メディアには標準の送信待ちトーストを使います。現在のアカウントに保留項目があれば、無効なプロバイダーの項目を含め、閉じる操作や再読み込みでブラウザー標準の未保存変更の確認を表示します。確認済みまたはアカウントの消去後に警告は解除されます。文言や事前のユーザー操作の要否はブラウザーが決めます。保留項目は再読み込み後も残り、警告によって破棄されることはありません。

ソーシャルのキャッシュはタブ内のみで、同意が必要です。初回訪問、非公開ページのオフライン再読み込み、ルーム作成、メンバー・キーの管理、通話、大容量アップロードには接続が必要です。入力中状態や一時的な在席通知は再送しません。送信時には現在のサーバー認可を確認し、切断中のキャッシュでは遠隔の権限取り消しを知ることはできません。アクセスと再送の前に ToS への同意が引き続き必要です。

## オフラインナビゲーション

Messages は、現在のアカウントとセッションのルーム一覧が保存され、ページのアセットが準備済みの場合だけオフラインナビゲーションを有効にします。会話には保存済みの暗号化メッセージとロック解除済みのキーリングが必要で、未保存の会話には接続が必要です。プロバイダーの再描画でもオフラインリンクの無効状態を維持します。

## 保存済みキューの結果

暗号化メッセージは、サーバー確認またはキューへの永続保存後にのみ下書きを消します。その後のチャット表示更新に失敗しても、送信失敗扱いにはしません。保留中のメッセージは再送用の安定した操作IDを保持します。

## オフライン利用の維持

Messages は認証済みのログイン後にルーム一覧、翻訳、絵文字カタログを準備します。ページのアセットとルーム一覧がキャッシュされていれば、オンラインで初めて訪れる前でもオフラインで開けます。メタデータと会話がキャッシュされたルームだけが自動的に開き、未保存の会話を選ぶと対象を明示した情報トーストを表示します。バンドルと直接配信されたファイルを繰り返し読み込んでも、ルーム登録とアセットの利用可否は保持されます。

## 独立した絵文字使用記録

Messagesの再利用可能なリアクション選択機能は、リアクション変更とは独立して絵文字の使用頻度を記録します。最終的な有効状態はメッセージのリアクション要求だけに含めます。使用記録に失敗してもログに残すだけで、選択したリアクションや更新コールバックを妨げません。

## ストレージとルートの型

ソーシャルプロフィールのロールと公開範囲の型を保存済みレコードに合わせました。メッセージとプロフィールのルートでは認可チェックを維持し、コールバック、通知、データベースコマンドに明示的な契約を適用します。ゲストセッションを解決できない場合は、従来どおりゲストプロフィールを読む前に失敗します。

## 認証情報の適用範囲

アカウント操作には検証済みのアカウントセッションが必要です。共有リソースの操作ではゲスト認証情報を明示的に検証し、リソースの権限を適用する前に現在の共有許可を再確認します。アカウント名から認証情報の種類を判断しません。取り消されたアクセスや有効期限切れのアクセスは拒否されます。

## メッセージの折り返し

標準、吹き出し、IRCの各スタイルで、メッセージ本文は会話欄の利用可能な幅に合わせて折り返されます。収まる短いメッセージは1行のまま表示されます。明示的な改行、Markdownの書式、HTMLに似た文字列の表示は維持され、空白のない長い文字列もメッセージ内で折り返せます。送受信のどちらにも適用され、アバター、リアクション、配信情報は変わりません。

## 会話の非同期更新

最後に選択した会話だけが、見出し、メッセージ、鍵、操作を更新できます。会話を切り替えるかMessagesから移動すると、保留中の表示更新は無効になります。下書きは現在のページが有効な間、元の会話に保持されます。

メッセージの送信中も次の下書きを書き始められます。送信確認または永続キューへの保存が完了すると、送信した版の下書きだけが消去され、その後の編集や他の会話の下書きは残ります。送信処理中の重複送信は防止されます。その後の会話更新に失敗しても、メッセージは送信済みまたはキューに保存されたままで、再送しないよう通知されます。

未読表示は既読状態の更新が確認された後にのみ変わります。失敗すると未読数を維持し、その失敗が続く間は翻訳された通知を1回だけ表示します。更新が成功した後に再び失敗した場合は、改めて通知できます。

バックグラウンド更新に失敗すると、翻訳された通知が表示され、現在の下書きは保持されます。繰り返す失敗は記録されますが、通知が再表示されるのは復旧後、または別の会話を選んだ後です。離れたルームやアカウントの遅延した失敗によって、古い送信エラーが表示されたり、追加の読み取りが始まったり、現在の会話が中断されたりすることはありません。メッセージ画面を離れて開き直した場合も、古い画面の保留中の更新は終了します。

リアクションの変更と過去のメッセージの読み込みは、開始した会話に紐づきます。現在の会話で失敗すると翻訳済みの通知を表示し、メッセージの内容を含めずに記録します。すでに離れたルーム、アカウント、ページでの失敗は無視されます。これらの操作は自動的には再試行されません。プレビューのチュートリアルでは書式、リンク、改行を説明し、添付ファイルは扱いません。

## メッセージのテキスト選択を維持

選択したメッセージ本文に変更がなければ、新着メッセージ、リアクション、閲覧者のメタデータで会話が更新されても、DOM の選択範囲、方向、位置を維持します。3種類の表示スタイルと、隣り合うメッセージにまたがる選択に対応します。選択した本文自体が変更または削除された場合は、ブラウザーの標準の選択規則に従い、古い本文を復元しません。

過去のメッセージを読み込む際も、ライブ更新で読み込み済みのメッセージが失われません。ローカルの送信待ちメッセージは、サーバーページの件数やページカーソルに含めません。同じページを繰り返し読み込んでも行は重複しません。上にスクロールした表示は基準位置を維持し、下端付近では新しい内容を追従します。ルーム、アカウント、鍵、スタイルの変更や再マウントでは別の表示として開始します。

表示中の古いメッセージへのリアクションが確認されると、オフラインキューへの永続保存を含め、有効状態を直ちに更新します。その後、既存のメッセージ一覧契約で対象ページのリアクションメタデータを更新し、変更のない本文は置き換えません。更新の読み取りが失敗した場合は、新しいメッセージでも古いメッセージでも更新エラーを表示し、確認済みの状態と選択中の本文を保持します。変更操作は自動再試行しません。

実 DOM の回帰テストには、リポジトリが対応する Node バージョンと互換性のある、バージョン固定のテスト専用 jsdom 開発依存関係を使用します。公開されたレンダラー、DOM ノード、Range/Selection、操作データ、実際のオフライン投影を検証します。指定した寸法でスクロール方針を検証しますが、ブラウザーのレイアウト、タッチ選択、クリップボード動作は測定しません。

送信待ちの投影には、サーバー履歴の統合とは別のリクエスト順序を使用します。遅れて届いた応答が新しい送信待ちメッセージを削除したり、消去済みの項目を復元したり、確認済みの行を送信待ちのコピーで置き換えたりすることはありません。変更のないポーリングでも順序を更新します。応答の送信待ち投影を破棄した場合は署名を無効にし、次回のポーリングで最新データを反映できるようにします。

最新ページのリクエストにも公開順序を保持します。遅れて届いたライブ応答が、新しい確認済みメッセージを削除したり、新しいメタデータを置き換えたりすることはありません。古い最新ページのスナップショットは破棄し、明示的な履歴リクエストは引き続き統合します。古いリクエストの失敗で、新しく表示した内容は消去されません。

読み取りと確認済みリアクションは、現在の表示内で同じ順序を使用します。重複する履歴の読み取りでは各メッセージの新しいメタデータを維持し、完全なライブページが確定した後に古い読み取りが存在しない行を復活させることを防ぎます。件数上限に達したページでは、最古の同一タイムスタンプにある行の不在を推測せず、`before` は境界を含みません。範囲情報は古い読み取りが進行中の間だけ保持します。それらの読み取りに対する優先順位が同じ重複範囲を統合し、読み取り終了後に削除するため、停止中の読み取りがあってもポーリングごとに範囲が増え続けません。新しい結果で置き換えられた後続読み取りのエラーは表示せず、現在の読み取りエラーと変更操作の失敗は表示します。

スコープ付きクライアントの `x-cognis-read-source` ヘッダーは、新しい通信（`live`）、開始済み通信への参加（`shared`）、保存または復元されたスナップショット（`cached`）を区別します。共有またはキャッシュされたサーバー行は、表示済みのメタデータを上書きせず、読み込み済みの行を削除しません。ライブ結果が履歴の終端を確定していなければ、未読の古い部分を補えます。空のキャッシュ範囲が示すのは現在読める履歴の終端だけで、後のライブ結果で再び読み込めます。送信待ちの投影は別に照合します。ソースを含む署名により、実際に新しい応答は古いスナップショットと同じ内容でも、保持されたメタデータを更新できます。

ルーム、アカウント、鍵、スタイル、コンテナーの所有状態が変わった場合、レンダラーは明示的な無効結果を返します。操作、ルームを開く処理、バックグラウンド更新の各呼び出し元は、エラー通知、既読状態の書き込み、入力状況の追加読み取りを行わず終了します。現在の読み取り失敗とは区別します。
