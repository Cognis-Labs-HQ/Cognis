# ドキュメント作成標準

## 概要

このドキュメントは、Cognisコードベースにおけるドキュメントの作成と整理方法を定義します。すべてのゲートウェイ、アダプター、モジュール、およびプラットフォームレベルのコンポーネントは、Markdownファイルとして独自のドキュメントを提供し、docsルートによって自動的に検出され、アプリ内ドキュメントブラウザを通じて提供されます。

目標は一貫性です。任意のドキュメントを読んだ貢献者は、セクション構造を即座に認識し、必要なものを見つけ、同じパターンに合う新しいドキュメントの書き方を知ることができるはずです。ドキュメントはエンドユーザーではなく、開発者の貢献者向けに書かれています。読者がHTTP、Node.js、TypeScriptを理解していることを前提とします。

ドキュメントは、それが説明するコードの隣に配置されます。ゲートウェイのドキュメントは `src/gateways/<id>/docs/` に、アダプターのドキュメントは `src/adapters/<gateway-id>/<adapter-id>/docs/` に、プラットフォームレベルの横断的なドキュメントは `src/docs/` に配置されます。docsルートは起動時にすべての `docs/` ディレクトリを自動検出するため、新しいドキュメントの追加に中央登録は不要です。

## 責任範囲

- すべてのコンポーネントドキュメントの標準セクション構造を定義する。
- モジュール、ゲートウェイ、アダプター、およびコア向けサーフェスの標準ルートレイアウトを定義する。
- ファイル命名規則と言語要件を定義する。
- 深度レベルを定義し、著者が各ドキュメントの詳細度を把握できるようにする。

担当外: ドキュメントの存在の強制（それはコードレビューの問題）、自動スペルチェック、リンクの検証。

## アーキテクチャ

### 標準コンポーネントルートレイアウト

新規または再編成されたコンポーネントは、貢献者がディレクトリツリーごとに別の規則を覚えなくて済むよう、同じトップレベルの責務名に収束させます。コンポーネントがドキュメント、サーバー、またはブラウザーのサーフェスを公開する場合は、そのコンポーネントルートに対応する `docs/`、`api/`、`ui/` ディレクトリ名を確保し、エントリーファイルを予測可能に保ってください。

| ファミリー                | ルート                         | 標準ルート             | 補足                                                                                                                                                                            |
| ------------------------- | ------------------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| プラットフォーム / コア層 | `src/`                         | `docs/`, `api/`, `ui/` | `src/docs/` は開発者向けドキュメント、`src/api/` は HTTP/サーバーコード、`src/ui/` はブラウザー資産を保持します。`src/core/` はプロバイダー非依存の契約とサービス層のままです。 |
| ゲートウェイ              | `src/gateways/<id>/`           | `docs/`, `api/`, `ui/` | ゲートウェイ所有のサーバーハンドラー、ルート登録、ブートストラップ補助は `api/` に、管理/ブラウザー資産は `ui/` に置きます。                                                    |
| アダプター                | `src/adapters/<gateway>/<id>/` | `docs/`, `api/`, `ui/` | `api/` はアダプター所有のブートストラップまたはサーバー補助、`ui/` はアダプターが公開するブラウザー資産の置き場所です。                                                         |
| モジュール                | `<module-repository>/`         | `docs/`, `api/`, `ui/` | `docs/` と `ui/` はモジュールドキュメントとブラウザー資産の安定した置き場です。`api/` はモジュール所有のサーバーコードの安定した置き場です。                                    |

`tests/`、`languages/`、`sql/`、`templates/`、`bootstrap/`、`cli/`、`db/`、`content/`、`reuse/` のような補助ディレクトリはこれらの横に置けますが、補完するだけで置き換えてはいけません。新規または再編成されたコンポーネントでは、トップレベルの `routes/` 兄弟ディレクトリより `api/routes/` を優先し、独自のドキュメントエントリーファイル名より `docs/index.<lang>.md` を使ってください。

### セクション構造

すべてのドキュメントファイルはMarkdownファイルです。セクションはこの順序で表示されます。深度レベルのルールで明示的に指定されている場合のみ、セクションを省略できます:

**1. `# コンポーネント名`** — 明確なH1タイトル。識別子文字列ではなく、コンポーネントの完全に読みやすい名前を使用します（例: `# 認証ゲートウェイ`、`# auth` ではなく）。

**2. `## 概要`** — コードベースに初めて触れる開発者向けの2〜4段落。このコンポーネントが何であるか、どのような問題を解決するか、Cognisに存在する理由を説明します。専門用語は避け、技術的な詳細はアーキテクチャセクションに残します。例:

> 認証ゲートウェイは、CognisにおけるすべてのログインおよびID操作の単一エントリーポイントです。ルートハンドラーと具体的な認証アダプターの間に位置することで、プラットフォームの残りの部分を特定の資格情報プロバイダーから切り離します。新しいIDプロバイダー（LDAP、SAML、またはカスタム社内システム）の追加には新しいアダプターのみが必要で、ルートハンドラーを変更する必要はありません。

**3. `## 責任範囲`** — このコンポーネントが所有し、責任を持つことの箇条書きリスト。リストの後に `担当外:` で始まる短い注記を付けて明確な境界を示します。例: `担当外: ユーザープロファイルデータの保存（それはプロファイルゲートウェイの担当）`。

**4. `## アーキテクチャ`** — 主要な設計決定、データフロー、主要なインターフェース。`src/gateways/auth/gateway.ts` のようなファイルパスの引用や、主要なインターフェースや型シグネチャを示す短いコードスニペットを散りばめた散文。このセクションは「高レベルでどのように機能するか?」という質問に答えるべきです。

**5. `## 設定`** — このコンポーネントのデプロイまたは設定時にオペレーターが触れる環境変数またはマニフェストフィールド。`変数 | デフォルト | 説明` の列を持つ表として表示します。オペレーターが設定するものが何もない場合は、このセクションを完全に省略します。

**6. `## 拡張ポイント`** — 別の貢献者がこのコンポーネントを拡張またはプラグインする方法: 実装するインターフェース、拡張を登録するメソッド、ライフサイクルの見え方。コンポーネントに拡張ポイントがない場合は省略します。

**7. `## APIルート`** — `メソッド | パス | 説明 | 認証` の列を持つHTTPルートの表。このコンポーネントによって登録されたすべてのルートを含めます。コンポーネントがルートを登録しない場合は省略します。

### 深度レベル

異なるコンポーネントタイプには異なる深度が必要です:

| レベル                  | コンポーネント                             | 必要なセクション                                         |
| ----------------------- | ------------------------------------------ | -------------------------------------------------------- |
| プラットフォーム / コア | `src/docs/` のプラットフォームドキュメント | すべてのセクションを完全に                               |
| ゲートウェイ            | `src/gateways/<id>/docs/`                  | より軽いアーキテクチャ; 設定 + APIルートを含める         |
| アダプター              | `src/adapters/<gw>/<id>/docs/`             | 完全な標準（該当するすべてのセクション）                 |
| モジュール              | `<module-repository>/docs/`                | 完全な標準; モジュールが提供する場合は APIルートを含める |

### コードスニペット

- すべてのコードブロックで2スペースのインデントを使用する。
- TypeScript/JavaScriptの文字列リテラルにはシングルクォートを使用する。
- 非自明な制約を説明する場合を除き、コードスニペットにコメントを追加しない。
- ファイルパスの参照はリポジトリ相対形式を使用する: `src/gateways/auth/gateway.ts`。

### テーブル

ヘッダー区切り行を持つパイプ構文を使用する:

```
| 列A | 列B | 列C |
| --- | --- | --- |
| 値  | 値  | 値  |
```

## 設定

この標準はCognisリポジトリのすべてのドキュメントに適用されます。ランタイム設定は不要です。

## 拡張ポイント

コンポーネントに新しいドキュメントを追加するには:

1. コンポーネントディレクトリ内に `docs/` サブディレクトリを作成する。
2. 上記のセクション構造に従った主要な英語ドキュメントとして `index.en.md` を追加する。
3. 対象言語の値を含む翻訳として `index.de.md`、`index.ja.md`、`index.id.md` を追加する。
4. docsルートは次のサーバー起動時にファイルを自動的に検出する。

複数のコンポーネントにまたがるプラットフォームレベルのドキュメントには、`<name>.en.md` を `src/docs/` に直接追加します（例: `src/docs/acl-matrix.en.md`）。これらはスラッグ `<name>` で提供されます。

### ファイル命名

| 場所                                      | 主要ファイル   | 翻訳ファイル                                   |
| ----------------------------------------- | -------------- | ---------------------------------------------- |
| プラットフォーム (`src/docs/`)            | `<name>.en.md` | `<name>.de.md`、`<name>.ja.md`、`<name>.id.md` |
| コンポーネント (`docs/` サブディレクトリ) | `index.en.md`  | `index.de.md`、`index.ja.md`、`index.id.md`    |

UIに表示される文字列には4つの言語（en、de、ja、id）すべてが必要です。翻訳がない場合、docsブラウザは `.en.md` にフォールバックします。

### 言語要件

翻訳ドキュメントのすべての文字列値は、そのファイルが表す言語で書かれていなければなりません。唯一の例外はブランド名（`Cognis`）、普遍的な技術略語（`LDAP`、`TLS`、`STARTTLS`）、フォーマットプレースホルダー、およびラテン語のタグライン（`Disce. Loquere. Vive.`）です。

翻訳版が存在するMarkdownドキュメントを変更する場合は、サポート対象のすべての言語の内容を同期したままにするため、同じ変更内で対応する各言語ファイルも更新しなければなりません。

## 機能ドキュメント規約

非公開のコントリビューター用テンプレート `.github/DOCUMENTATION_TEMPLATE.en.md` は、すべての実ドキュメントファイルに必須の開始順序を定義します。H1 の直後には、文書化する機能またはサーフェスが何を実現するかを説明する情報文を置きます。次の H2 には、インポート、機能解決、ルート呼び出し、構成、期待結果の具体的な使用例を記載します。その次の H2 から完全な技術仕様を開始し、入力、出力、ライフサイクル、検証、認可、エラー、副作用、永続化、セキュリティ、クリーンアップ、拡張の詳細をその中または H3 サブセクションに記載します。アーキテクチャテストは、変更履歴以外の全ドキュメントの最初の三つの見出しレベルを非公開テンプレートと比較します。
