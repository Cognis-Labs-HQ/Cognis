# 特権アカウントの境界

**機能ブランチ:** feature-auth-tfa-target-policy

## アカウント対象を保護

特権アカウントの認可を Auth に統一し、回復コードの再発行と管理者リセットを含む、すべての別アカウントへの TFA 読み取りと変更の前に適用します。所有者の権限と本人向け操作を維持し、ポリシーの利用不可、不明なアカウント、古い有効期間を拒否します。ユーザー管理も同じ契約を使用し、操作固有の制限を維持します。

## 提供元の契約を検証

実際の段階的ポリシーと登録済みルートを使い、合成ロール、創設者情報、存在しない対象、不正入力、機能の失敗、遅延した有効期間の変更をテストします。Auth 2.2.12、TFA 1.3.13、API 0.13.36 と四言語の統合ガイドを同期します。

## 変更直前の再検査

Users はリクエスト準備後に、Auth は登録解除の最初の変更直前に認可を再取得します。実行者の識別情報を不変に保ち、遅れて発生したロール・創設者の変更や有効期間の終了を拒否し、正当な管理者昇格ではプロフィール同期を完了します。LDAP システム同期を区別し、一部完了の境界を文書化します。遅延した本文、メタデータ、フロー段階、不正なガードの恒久的な回帰テストを追加します。

TFA 設定と Users のロール変更の失敗には既存の翻訳済み代替メッセージを使い、任意のサーバーコードを翻訳キーとして扱ったり、生のポリシーコードを表示したりしません。既存チュートリアルに新しい操作や手順は不要です。

## 後処理結果の真正性を検査

Auth で登録解除の証明を元の入力と呼び出しに結び付け、Users とすべての同梱後処理利用側で所有者の正式な結果を要求します。完了済みの変更を再認可せず、後段の結果偽装や別の実行結果の再利用を拒否します。所有コンポーネントのバージョン、検証済み依存上限、4 言語の導入説明を更新します。監査した旧 Jitsi モジュールは導入上の依存事項として残ります。環境を保護済みと扱う前に、その後処理フックを移行するか無効化してください。

## 呼び出しコンテキストを保持

Core 0.6.6 は既に readonly と宣言されたフローコンテキスト参照を浅く凍結し、入力・data・結果の内部の変更とステージ順序は維持します。Auth は実行時にこの保証を検査し、旧ランナーを拒否します。保存済みの入力と結果の組の再利用、混在バージョン、実際の汎用ランナーのテストを追加します。23 個の検証済み Core 上限を更新し、公開ワークスペースへの解決を検証します。リポジトリと外部モジュールの静的監査では、対応対象のトップレベル参照代入は見つかりませんでした。
