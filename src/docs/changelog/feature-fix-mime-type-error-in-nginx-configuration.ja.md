# 安定した UI アセット読込

## アセットエラーのキャッシュを防止

Web プロキシと API は、見つからないフィンガープリント付き JavaScript および CSS の応答が不変アセットとしてキャッシュされないようになりました。デプロイの切り替えが重なっても、アセット URL の JSON 404 応答を保持せず、クライアントが正常に復旧できます。

## ログインページの描画を復旧

ページコンポーザーがすべてのレイアウト処理に要素レンダラーを渡すようになり、スタイルと内容の読み込みが完了する前にログインページが `renderElementContent is not defined` エラーで停止する問題を解消しました。

## Web プロキシが実行環境のサービス名を解決

Nginx がコンテナ環境の標準的なホスト名解決を通じて Cognis アプリケーションサービスを解決するようになりました。Docker、Kubernetes、Podman、その他のコンテナプラットフォーム内の別のツールと同じ検索ドメインおよびホストマッピングを利用するため、Web コンテナ内の別の場所ではホスト名が有効なのに `no live upstreams` となる問題を防ぎます。

Web プロキシはサービス名を `cognis` と仮定せず、`HOST` からアプリケーションサービスのホスト名を取得します。`cognis.cognis` のようにピリオドを含む名前空間修飾名にも対応し、Kubernetes などのスコープ付きサービス名を使用するデプロイでアップストリームが空になることを防ぎます。

## アセット要求パスを変更せず転送

nginx テンプレートは `/assets/` 専用のプレフィックスロケーションを使用し、URI を書き換えずに転送するようになりました。これにより、フィンガープリント付き JavaScript および CSS の要求が、ファイル名パターンの一致に依存せず、要求されたパスのまま Cognis のアセットハンドラーへ届きます。

## デプロイに依存しないコンテナ起動

アプリケーションのエントリポイントは、Cognis の実行前に構造化ログとプロバイダー固有項目からの任意の `DATABASE_URL` 生成を復元しました。`DATABASE_URL` や `DATA_ENCRYPTION_KEY` などの機密値にはイメージ既定値を設けず、デプロイ環境から提供する必要があります。Web プロファイルは Cognis 専用 nginx イメージをビルドせず、汎用 nginx イメージと標準の環境変数置換テンプレートを使用します。

## 本番イメージのビルド時だけ開発ツールを導入

アプリケーションイメージは、`NODE_ENV` が `production` でも esbuild などのツールを使用できるよう、ビルド段階で開発依存関係を明示的にインストールします。コンパイル済み UI とサーバーの検証後に開発専用パッケージを削除するため、実行時イメージには含まれません。

## Compose のデータベース設定をエントリポイントと統一

PostgreSQL および MariaDB の Compose プロファイルは、アプリケーションのエントリポイントが使用するプロバイダー固有のホスト、ポート、データベース、アカウント、パスワード項目をそのまま渡すようになりました。重複する組み立て済み URL を要求せず、Cognis が一貫して `DATABASE_URL` を生成します。

## 開発依存関係なしで cognisctl を実行

コンテナのラッパーは、tsx で TypeScript ソースを読み込まず、コンパイル済み Cognis CLI を直接起動するようになりました。これにより、本番イメージから開発専用パッケージを削除した後も CLI を利用できます。

## ランタイムと依存関係を更新

アプリケーションイメージと CI は、最新の Node.js 24 LTS 系列を使用するようになりました。ビルドツール、TypeScript、データベースクライアント、LDAP クライアントを最新の安定版へ更新し、Docker ビルドコマンドでは非推奨の npm `http-proxy` 設定警告を抑制します。すべてのコンポーネントバージョンと内部依存関係の検証済み上限を引き上げ、マニフェスト、ロックファイル、翻訳済みバージョン一覧で同期しました。

## ログイン処理を目的別モジュールへ分割

ログイン連携の検出と認証済みセッションの保存を、ログインページが所有する専用モジュールへ移しました。ログインのエントリポイントは同じセッション動作を維持しながらソースファイルのサイズ制限を下回り、認証状態の保存と削除には直接的な回帰テストも追加されています。

## SMTP 初回送信判定を決定的に処理

SMTP レートリミッターは、時刻を読み取る前に対象受信者の送信記録が存在するか確認するようになりました。時刻の読み取り間にシステム時計が後退しても新しい受信者を誤って制限しないため、記録済み送信の制限期間を維持しながら Node.js 24 CI の断続的な失敗を解消します。

## コンテナ検証を実行結果に集中

コンテナ設定の文字列を重複して検査する過剰なツールテストを削除しました。コンテナのビルドとアプリケーションテストを合否判定として維持し、設定書式の付随的な詳細ではなく、ビルド済みアプリケーションが動作するかどうかに保守作業を集中させます。
