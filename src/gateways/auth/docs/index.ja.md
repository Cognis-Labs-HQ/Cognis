# 認証ゲートウェイ

## 概要

認証ゲートウェイは、Cognisにおけるすべてのログインおよびアイデンティティ操作の単一のエントリポイントです。ルートハンドラーと具体的な認証アダプターの間に位置することで、プラットフォームの残りの部分を特定の認証プロバイダーから切り離します。認証プロバイダーの切り替え（ローカルパスワードからLDAPやSAMLへ）は、管理者APIで新しいアダプターを有効にするだけで済みます。ルートハンドラーやコアサービスの変更は不要です。

ゲートウェイはブートストラップ時に `src/adapters/auth/` をスキャンしてアダプターを検出します。各アダプターディレクトリは `createAdapter()` 関数をエクスポートする必要があります。ローカルアダプターは常に最初に読み込まれ、`user:*` CLIコマンドと初期管理者アカウント作成フローを支援するため特別に扱われます。他のすべてのアダプターはディレクトリから読み込まれ、サーバーを再起動せずに管理者が実行時に有効・無効を切り替えられます。

## 責務

- ブートストラップ時に `src/adapters/auth/` からすべての認証アダプターを検出・登録する。
- `auth_adapter_configs` に永続化されたアダプターの有効・無効状態を管理する。
- 要求されたプロバイダーの有効なアダプターに委譲して認証情報を検証する。
- 認証成功後に `issueAccessToken` でアクセストークンを発行する。
- 文書化されたケイパビリティ一式を提供する：`auth:accountStore`、`auth:createLocalAdmin`、`auth:getLoginMethods`、`auth:registerProvider`、`auth:registerLoginButton`、`auth:registerPageScriptOrigins`、`auth:issueAccessToken`、`auth:getAuthClaims`、`auth:requireAuth`、`auth:requireRoleAccess`、`auth:revokeAccessTokensForSubject`、`auth:revokeSetupPendingAccessTokens`、`auth:routeContext`。
- すべての認証APIルートとアダプター管理ルートを登録する。

責務外: ユーザープロフィールデータの保存（プロフィールゲートウェイの責務）、トークン発行を超えたセッション管理、非認証ビジネスロジック。

### 実行時プロバイダーのライフサイクル

実行時ブラウザー向け OAuth リダイレクトでは `/sso/<routeNamespace>/<path>` を使用できます。Cognis はクエリ形式のコールバックをプロバイダーへ直接渡し、フラグメント形式の応答も同じサーバー所有コールバックへ橋渡しするため、読み込み表示が残り続けません。コールバック失敗時は、ローカライズされたエラーとともにログインへ戻ります。

プロバイダーは LDAP と同様に、認証ゲートウェイを設定と電源状態の権限元として使用する必要があります。プロバイダーは安定した `id`、`getConfigSchema()`、`configure(config)`、`isConfigured()` を提供し、管理画面は `/api/v1/gateways/auth/adapters/<id>/config` を読み書きし、`/enable` または `/disable` で切り替えます。モジュール側で別の有効化フラグを保持したり、モジュールの有効化をアダプターの有効化と同一視したりしてはいけません。

ブートストラップでは、ルートやログイン表示を登録する前に `auth:registerProvider(provider, requires)` を待機します。この Promise は、Cognis がアダプターの保存済み設定と有効状態を復元した後にのみ完了します。その後にブランド付きボタンを登録し、両方の破棄関数を保持し、終了処理ではプロバイダー登録を解除する前にボタンを削除します。保存済みの有効状態がないプロバイダーは無効状態で開始し、ゲートウェイ所有のアダプター設定フローでセットアップを完了する必要があります。

## アーキテクチャ

中心クラスは `src/gateways/auth/gateway.ts` の `CoreAuthGateway` です。登録されたアダプターのマップ、有効なアダプターIDのセット、ローカルアダプターへの参照（`setLocalAdapter()` で別途設定）を保持します。

```ts
export class CoreAuthGateway {
  registerAdapter(adapter: AuthProviderAdapter, requires?: string[]): () => boolean;
  setLocalAdapter(adapter: AuthProviderAdapter & { ... }): void;
  async discoverAdapters(authAdaptersRoot: string): Promise<void>;
  async loadPersistedConfigs(): Promise<void>;
  async getEnabledAdapter(id: string): Promise<AuthProviderAdapter | null>;
  async getAdapter(): Promise<AuthProviderAdapter | null>;
  async authenticate(credentials: Record<string, unknown>, providerId?: string): Promise<AuthContext | null>;
  async createLocalAdmin(username: string, password: string): Promise<AuthContext>;
  async getLoginMethods(): Promise<AdapterInfo[]>;
}
```

`getEnabledAdapter(id)` は特定のアダプターが現在有効な場合のみIDで返します。`getAdapter()` （引数なし）は最初の有効なアダプターを返します。適切なアダプターが見つからない場合は両方とも `null` を返します。

`registerAdapter()` は、モジュールの破棄処理が使用するプロバイダーのクリーンアップ関数を返します。呼び出すと、そのプロバイダー登録、有効化状態、依存関係メタデータだけが削除されます。同じIDが別のプロバイダーに置き換えられている場合、置き換え後のプロバイダーは削除されません。モジュールを無効化すると、そのモジュールが提供したすべてのケイパビリティを取り除く必要があるため、このクリーンアップが必要です。

`src/gateways/auth/bootstrap.ts` と `src/gateways/auth/bootstrap/` でのブートストラップ:

1. `src/adapters/auth/local/store.ts` から `DbLocalAccountStore` をインスタンス化。
2. DBエグゼキューターとタイプで `CoreAuthGateway` をインスタンス化。
3. `setLocalAdapter()` でローカルアダプターを読み込む。
4. `discoverAdapters(authAdaptersRoot)` を呼び出して他のすべてのアダプターを読み込む。
5. `loadPersistedConfigs()` を呼び出してデータベースから有効・無効状態を復元。
6. `src/gateways/auth/bootstrap/` の capability / bootstrap hook を実行。
7. ルートとケイパビリティを登録。

提供されるケイパビリティ:

| ケイパビリティ                   | 型                                             | 説明                                                                            |
| -------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------- |
| `auth:accountStore`              | `LocalAccountStore`                            | ローカルアダプターが使用するローカルアカウントストア                            |
| `auth:createLocalAdmin`          | `(username, password) => Promise<AuthContext>` | 存在しない場合に管理者アカウントを作成                                          |
| `auth:getLoginMethods`           | `() => Promise<AdapterInfo[]>`                 | すべての有効なプロバイダーのメタデータを返す                                    |
| `auth:registerProvider`          | `async (provider, requires?) => dispose`       | モジュール認証プロバイダーを登録し、そのクリーンアップ関数を返す                |
| `auth:registerLoginButton`       | `(descriptor) => dispose`                      | ブランド固有のログインボタン表示を登録し、そのクリーンアップ関数を返す          |
| `auth:registerPageScriptOrigins` | `(ownerId, origins) => string[]`               | ページのCSPヘッダーで1つの所有者の信頼済みhttp(s)スクリプトオリジンを置き換える |

認証プロバイダーは `auth:registerProvider` を待機してから `auth:registerLoginButton` を呼び出す必要があります。登録処理は完了前にアダプターの保存済み設定と有効状態を復元し、LDAP のようなファイルシステム検出プロバイダーと同じライフサイクルになります。記述子には、登録済みの `providerId`、完全にローカライズされた `label`、同一オリジンの `iconUrl` が必要です。任意の `backgroundColor`、`borderColor`、`textColor` には 6 桁の 16 進色を使用します。ログインページは、コンパクト表示とワイド表示の両方でアイコンと完全なラベルを常に表示します。プロバイダーは、提供を無効にするときに返されたクリーンアップ関数を呼び出す必要があります。 スタイルが指定されていない非認証情報方式は、汎用ログインボタンとして表示せず除外されます。

プロバイダーはアダプターに `routeNamespace` と `registerRoutes(router)` を宣言できます。ルーターは `/api/v1/auth/<routeNamespace>` からの相対 `GET` および `POST` パスを受け付けるため、提供元モジュールに保護されたコアルートへの直接アクセスを与えず、OAuth コールバックを認証ゲートウェイ配下に配置できます。名前空間は安全な URL セグメントに制限され、認証コアの名前空間は予約され、重複ルートは拒否され、プロバイダーを削除すると提供されたすべてのルートも削除されます。

外部プロバイダーのセッションは、`ensureExternalAccount` の前に `gateAccountCreation` を通過します。有効な公開登録アダプターは、ローカルアカウントの公開登録ポリシーとは独立して SSO アカウントの作成を許可します。それ以外の場合、Cognis は未知の認証済み ID を有効期限付きの不透明な処理 ID で保持し、`registrationUrl` を含む `account_creation_required` を返します。プロバイダーはその URL にリダイレクトします。登録トークンアダプターが標準の登録画面に認可フォームを追加し、プロバイダーのコールバック状態を公開せずに保留中の ID の処理を再開します。

## APIルート

| メソッド | パス                                         | 説明                                         | 認証     |
| -------- | -------------------------------------------- | -------------------------------------------- | -------- |
| `GET`    | `/api/v1/auth/login-methods`                 | 有効な認証プロバイダーを一覧表示             | 不要     |
| `POST`   | `/api/v1/auth/register`                      | 新しいローカルアカウントを自己登録           | 不要     |
| `POST`   | `/api/v1/auth/login`                         | 認証してBearerトークンを返す                 | 不要     |
| `POST`   | `/api/v1/auth/sso/start`                     | 外部プロバイダーの認可リダイレクトを開始する | なし     |
| `POST`   | `/api/v1/auth/verify`                        | 現在のユーザーのパスワードを検証             | ユーザー |
| `GET`    | `/api/v1/gateways/auth/adapters`             | 登録済み認証アダプターを一覧表示             | 管理者   |
| `GET`    | `/api/v1/gateways/auth/adapters/:id/config`  | アダプターの設定スキーマを取得               | 管理者   |
| `PUT`    | `/api/v1/gateways/auth/adapters/:id/config`  | アダプターの設定を更新                       | 管理者   |
| `POST`   | `/api/v1/gateways/auth/adapters/:id/test`    | アダプター設定をテスト                       | 管理者   |
| `POST`   | `/api/v1/gateways/auth/adapters/:id/enable`  | アダプターを有効化                           | 管理者   |
| `POST`   | `/api/v1/gateways/auth/adapters/:id/disable` | アダプターを無効化                           | 管理者   |

アダプターテストの失敗には、任意の数の設定項目 ID を安全な診断メッセージに対応付ける `error.fieldErrors` オブジェクトが含まれる場合があります。

アダプターがローカライズ済みの管理リソースを所有する場合、アダプター一覧と設定契約に `stringsBaseUrl` が含まれます。

## ブラウザーキーリング起動

認証ゲートウェイは、ブラウザーセッションフックを登録する前に必須キーリングアダプターを読み込みます。これにより、ページの直接読み込みや再読み込みのたびに、現在のタブの抽出不可能なセッション鍵を自動復元できます。復元できない場合は、保護されたコンテンツを最初に解決するときにコンテキスト付きキーリング解除ダイアログを開きます。

## 共有失敗理由の伝達

ブラウザーセッション結果は中立な代替認証失敗理由を保持するため、公開リソースページは認証内部を import せずに、存在しないリソースとその他の利用不可状態を区別できます。

認証ソースの変更は、永続化後に `reconcile-auth-sources` フローを実行します。アダプターフックは `reconcile-accounts` ステージを使用し、ルート側でプロバイダー分岐を行わずにセッション失効とソース所有の識別情報調整を実施します。

## ブラウザーセッションの境界

パスワード確認の無効化は、認証済みの完全なアカウントセッションでのみ実行されます。匿名ページや Share ゲストページの初期化では、アカウント専用の `DELETE /api/v1/auth/verify` 要求を送らずにキーリング状態をロックまたは置換できます。

## 外部プロフィールプロバイダー

SSO モジュールは CTX を介して `auth:registerExternalProfileProvider` を登録できます。リゾルバーはプロバイダー ID、Cognis アカウント ID、外部ユーザー ID、認証済みプロバイダーセッションを受け取り、検索可能なハンドル、表示名、自己紹介、所在地、Web サイト、アバターおよびバナーのデータを返せます。プロバイダーセッションに `handle` または `username` がある場合、Cognis は不透明な外部アカウント ID ではなく、その値を初期プロフィールハンドルとして使用します。プロフィールアダプターが外部アカウントの初回作成時に自身の保存機能で反映します。有効な `profileVisibility` 値（`hidden`、`private`、`friends`、`community`）は、新しいプロフィールの公開範囲として保存されます。

### 外部プロフィールの同期

外部認証連携は CTX クエリ `auth:syncExternalProfile` を提供できます。このクエリは認証済みアカウントの `{ providerId }` を受け取り、`auth:resolveExternalProfile` を介してプロバイダー所有のプロフィールを更新し、Cognis がプロフィールおよびファイルのケイパビリティを通じてハンドル、表示項目、アバターデータ、バナーデータを保存した後にのみ完了します。プロバイダーの画像 URL は連携への入力に限定し、ブラウザー画面が常に Cognis 所有のファイルを表示できるよう、クエリはメディアデータを返す必要があります。ブラウザーでは、連携機能がプロバイダー ID と同期関数を指定して `auth:registerExternalProfileSynchronizer` を呼び出します。認証機能が所有するレジストリは現在のプロバイダーにだけ操作を公開するため、別の導入済み連携が誤ったアカウントプロフィールを処理または上書きすることはありません。

### 削除済みの外部 ID

外部認証アカウントを削除すると、アカウント所有データを削除する前に、そのプロバイダー ID の一方向フィンガープリントが保存されます。その後プロバイダー認証に成功すると、ディレクトリベース認証と同様に、アカウントの再作成と同じトランザクションで削除記録が消去されます。認証に失敗した場合は記録を消去できず、フィンガープリントはブラウザークライアントには公開されません。

### プロバイダー別のアカウント名

新しい外部アカウントでは、ローカルアカウントキーとプロフィールハンドルの両方にプロバイダーの名前空間を使用します。`accountNamespace` が `x` のプロバイダーセッションでハンドルが `firehawksystems` の場合は `x:firehawksystems` となり、ローカルの `firehawksystems` アカウントや `line:firehawksystems` などの ID とは区別されます。既存の `(provider, external_user_id)` マッピングは、プロバイダーのハンドルが変わっても、以後のログインで引き続き優先されます。

## ブラウザのメディアポリシー

認証済みページでは、同一オリジンのルートとブラウザが生成した `blob:` URL のメディアを許可します。これにより、任意の外部メディアオリジンを許可せずに、信頼済み UI クライアントが認証済み音声レスポンスを再生できます。

### モジュールのライフサイクル統合

`auth:registerKeyringDataOwner(ownerId, purge)` は公開サーバー機能です。所有者 ID の重複を拒否し、登録の同一性を検証する解除関数を返します。モジュールは `module:<id>` を使い、`ctx.registerDisposer` に解除関数を登録します。purge は正規化したアカウント ID を受け取り、Keyring 依存状態のみを消去し、アカウント識別情報と無関係な共有資源を保持します。

## セッション設定

復元したSSOセッションを含め、認証済みセッションは `/api/v1/auth/setup-status` を確認します。Authが `auth:getSetupIntegrations(accountId, role)` を所有し、登録された確認モードを評価します。提供元は `enforceSetup({ accountId })` を公開する同一オリジンのスクリプトを渡します。必須設定を完了してから画面移動やオフライン利用を許可し、提供元が利用不可でもポリシーを免除しません。創設者管理者による復旧は例外です。

## ログインの進行表示

資格情報、TFA コード、SSO 認可の要求中は共通の読み込み表示を出し、対話的な設定の前に閉じます。処理中の資格情報の重複送信は無視します。公開オフラインキャッシュの整理と更新はログイン後にバックグラウンドで行います。ローカル認証アダプターが無効でも SSO の最終ログイン日時を記録します。

## アカウントのプライバシーとキーリングの分離

SSO アカウントにはプロバイダーを示さないランダムな ID を使用します。プロバイダー ID は別に保存し、管理者だけに表示します。公開ユーザー名には含めません。Auth はプロフィールやメールの変更前にユーザー名を確保します。同じプロバイダー内の重複名は拒否し、別プロバイダーとの重複には短いランダムな接尾辞を付けます。ユーザー一覧と操作 API は公開用の `username` と内部用の `accountId` を区別します。

従来の SSO レコードが存在していても、既存のローカルアカウントは引き続き使用できます。起動時にデータベースのリセットは必要ありません。従来の SSO アカウントのログインと作成処理だけを個別に拒否し、不透明な ID での再作成を必要とします。アカウント ID、関係、会議の自動移行や自動削除は行いません。

## ログインと保留中の送信

パスワードまたは TFA のログイン成功後は、既存の SPA ナビゲーション機能でログイン画面を Dashboard に置き換えます。検証済みタブと保留中の変更を維持し、ブラウザーのページ終了警告を発生させません。移動完了まで読み込み表示を維持し、任意のタイムゾーン同期はその後に実行してアカウント変更を拒否します。認証済みタブを閉じるか再読み込みする際は、実際に保留中の変更がある場合に引き続き警告します。

## セッションとコンポーネントの分離

Authは、検証済みオフラインアクセスの判定元として、通信を行わない同期機能`session:isOfflineValid`を公開します。設定完了状態、現在のアカウントとトークン、セッション期限を確認します。キューの所有者は認証ストレージを独自に解釈せず、この契約を利用します。代替ゲストセッションは通常のアカウント設定を省略します。サーバーのsetup-statusは、TFAやメール連携を要求する前にShareの分類機能を使用します。通常のローカルおよびSSOアカウントの設定義務は維持します。

## アカウントに結び付くキュー

キューの各レコードにサーバーが検証したアカウントインスタンス識別子を保存します。Authは認証済みの設定状態に正規の`accountInstanceId`を返し、検証済みで設定が完了し期限内のアカウントセッションにだけ`session:getOfflineIdentity`を提供します。信頼できるメタデータが欠けるとオフライン認可を取り消します。キュー表示、保存、配信の確認はこのインスタンスに結び付きます。同じアカウントIDでローカルアカウントを再作成した場合も、廃止済みまたは所有元不明のレコードは送信前に拒否します。操作IDがアカウントインスタンスを越えて衝突することはありません。Bearerトークンはキューに保存しません。

## SSO登録試行の有効期限

招待が必要なSSO識別情報は、アカウント、プロフィール、メールの作成前に保留します。取り消し済み、期限切れの試行は再開できません。登録と二要素認証は期限ちょうどで失効します。公開登録アダプターが有効なら、通常アカウントの公開登録設定とは別にSSOアカウントを作成できます。既存のアカウントを提供元や経過時間だけで削除することはありません。

## 登録可能なアカウント確認

`auth:userValidationModes.register` はID、翻訳キー、任意の言語リソース、必須登録フィールド、利用可否関数、確認関数、任意の設定画面連携を受け取ります。登録はブートストラップ中に限定し、提供元のライフサイクルに従います。AuthはメソッドIDで分岐せず、`auth:evaluateUserValidation` の `resolvePolicy`、`validateAccount`、`verifyResult` で選択した関数を実行します。設定済みのポリシーが存在しない、または利用不可の場合はアクセスを拒否します。創設者管理者による復旧は引き続き例外です。管理画面は登録メタデータを表示し、利用できなくなった保存済みの選択肢も保持します。

アダプター契約の登録は[共通ゲートウェイブートストラップ契約](/docs/gateways)に従います。

## 最終セッションの保証

Auth 所有のバージョン 1 機能 `auth:login` は `auth:prepareLogin`（`authenticate`、`assessSession`、`authorizeSession`）を実行してから `auth:completeSession` を呼び出します。一次フロー `login` は `authenticated` の準備データを返し、通常のトークンは発行しません。必要なアカウント情報の作成は準備段階で継続します。完了したログインには生のフローではなく機能を呼び出してください。本番ルートと登録済みフローのテストはこの境界を使用し、TFA 検証と設定は最終機能を呼び出します。既存の一次拡張は保証と確定の前に完了します。

`auth:completeSession` はバージョン 1 の信頼されたサーバー機能です。読み取り専用の `auth:prepareSession`（`validateAccount`、`validateLifecycle`、`authorizeSession`）でアカウントと任意のプロフィール状態を確認します。両方の準備フローは戻り値、データ変更、例外による拒否を有効化前に反映します。全拡張の完了後、Auth がアカウントごとに直列化して有効化とトークン発行を確定し、その後の方針フックはありません。存在するプロフィール提供元の失敗は `session_unavailable` となり、未導入構成は引き続き対応します。最終ログインの記録は保証後です。保証は所有元の試行と要素検証から得られ、リクエストの完了フラグは使用しません。ライフサイクル検査で古い処理を拒否します。失敗した確定では、その操作が発行した通常トークンだけを失効させます。コンポーネント間の保存はトランザクションではなく、全検査成功後の最終書き込みが保存してから失敗した場合や後続の確定処理が失敗した場合、有効化が残る可能性があります。他のプロフィール変更を巻き戻しません。未完了、無効、放棄された要素で有効化や通常トークンの残存は生じません。

TFA はバージョン 1 の `tfa:assessSession` 機能と段階的フローを提供します。既知の有効な TFA ゲートウェイで評価が動作しない場合は、安全のためログインを拒否します。意図的に未導入、または管理者が無効化した TFA は任意のままです。提供元の障害時も保存済みの有効な登録は必須として扱い、復旧コードは引き続き利用できます。保存済みの管理者による無効化は、その提供元の要件を明示的に解除します。任意の発行元メタデータのエラーで、有効な提供元が除外されることはありません。

要素の検証と設定完了は、いずれも Auth 所有の最終確定を使用します。`auth:consumePendingLoginAttempt` は要素の検証成功後、有効期限内の一次認証済み試行を不可分に消費します。同時または繰り返しの完了では再利用できません。設定の検証でも、同じ設定の同時完了を防ぎます。最終確定が失敗した場合、通常のトークンや Cookie は返しません。原因の解消後に再ログインしてください。所有元の終了処理で評価・確定フローと保留中のログイン試行を削除し、古い実行中の処理は安全に拒否します。既存のログインと設定チュートリアルの操作や進行は変わらず、利用できないセッションには翻訳済みのエラー通知を表示します。

## 型付き認証境界

Auth と TFA の宣言は、既存のアカウントロール、外部識別情報、データベースコマンド、Cookie セッションの投影を表します。セッションタイムアウトの検証で受け入れる数値は変わりません。ログインの保証と一度だけ使用できる要素認証の試行も維持されます。

## 制限付きトークンの管理

保存形式2ではセキュリティ項目の明示が必要です。未対応の形式、不正または曖昧なレコードは拒否されます。拒否されたセッションでは再ログインが必要で、形式の自動変換は行いません。有効な通常、制限付き、失効済みの認証情報は再起動後も権限状態を維持します。保存に失敗した場合は成功として扱わず、エラーを報告します。

auth:revokeSetupPendingAccessTokensケイパビリティは引数を受け取らず、設定待ちのすべてのセッションを失効させます。アカウント単位の除外はサポートしません。

## 認証情報の適用範囲

アカウント操作には検証済みのアカウントセッションが必要です。共有リソースの操作ではゲスト認証情報を明示的に検証し、リソースの権限を適用する前に現在の共有許可を再確認します。アカウント名から認証情報の種類を判断しません。取り消されたアクセスや有効期限切れのアクセスは拒否されます。

## 登録の完了

公開登録と招待の引き換えは、ログインセッションではなく、有効期間30分のオンボーディング資格情報を返します。通常のアカウントAPI、ブラウザーの本人識別、セッション更新、認証要素の確認には使用できません。その後、通常のログインと最終的なTFA確認が必要です。

Authはバージョン1のauth:onboarding契約を所有します。registerOperation({id, available?, execute})は呼び出した提供元の現在の起動スコープを取得し、IDはその所有者に属する必要があります。重複登録は拒否されます。削除、起動失敗、再有効化により実行中の処理も無効になります。listOperations()は一時的に利用できないハンドラーも含む登録済みIDを返しますが、この情報は権限ではありません。issue(accountId)はアカウントの存在を確認します。検証待ちのアカウントが有効化済みである必要はありません。

POST /api/v1/auth/onboarding/operationsは{operation, input}を受け取ります。Authは目的、有効期限、アカウント、提供元の存続を確認し、準備フローの後、その拡張可能なフローの外でハンドラーを実行します。フローの直接呼び出しでは操作を実行できません。ハンドラーは{accountId, assertCurrent}を受け取り、非同期処理後の各変更直前にassertCurrentを待機する必要があります。要求内のアカウントID、通常の所有者権限、共有ゲストの識別を使用しないでください。入力検証は提供元が行います。既知のエラーは、400、409、422、429、503のstatusと、小文字とアンダースコアによる短いcodeを持つ{status, code}のみを返せます。予期しないエラーは内部情報を含まないonboarding_operation_failedになります。

POST /api/v1/auth/onboarding/completeは完了またはキャンセル時に資格情報を失効させ、セッションには交換しません。通常のログイン成功時と未確認アカウント削除時にも、そのアカウントのオンボーディング資格情報だけを失効させます。中断された要求も有効期限で制限されます。保存形式2はオンボーディング目的、ユーザーロール、ローカル提供元、設定待ちでない状態、30分以内の期限を明示的に検証します。

トークンファイル、提供元のデータベース、配信は単一のトランザクションではありません。後続の検査や保存が失敗しても、完了済みの変更は残る場合があります。ページ終了時や通信障害時の後処理は可能な範囲で行い、配信を保証しません。

失効はこのプロセス内では直ちに有効ですが、トークンファイルへの書き込みが失敗すると、再試行に成功するまで以前の権限がディスク上に残る場合があります。保持されている失効済み資格情報の完了処理は冪等であり、保存を再試行します。アカウントの読み取り、非同期の提供元可用性確認、提供元の変更は保存先をまたいで不可分ではありません。発行機能は信頼されたサーバー用であり、要求のアカウントIDに資格情報を発行する公開エンドポイントではありません。

## 保留中のログインの継続

SSOプロバイダーが第1要素を受け入れた後、第2要素を設定したアカウントは `/login` に戻り、送信済みのコードを入力します。検証前にセッションを発行したりプロフィールを再有効化したりしません。「再試行」は一時的な読み込み失敗後に保留中の画面を再取得し、「キャンセル」はその試行を破棄して通常のログインに戻ります。再読み込みではメールを再送信しません。

Auth 2.2.10は `GET /api/v1/auth/login-attempt` と `DELETE /api/v1/auth/login-attempt` を追加します。GETは `{data: null}`、または `tfaRequired`、`loginAttemptId`、方式の記述子、`loginUrl: "/login"` を含む既存のTFA画面データを返します。DELETEはJSON `{loginAttemptId}` を受け取り、要求元ブラウザーのCookieと完全に一致する試行だけを取り消します。ルートはAuth所有の `auth:loginContinuation` フローの `validateRequest`、`applyContinuation` 段階を実行します。アカウントの認可と要素の検証は変わりません。

`cognis_login_attempt` CookieはHttpOnly、SameSite=Laxで、範囲は `/api/v1/auth`、Secure属性は既存のCookie方針に従います。元のサーバー所有の有効期間5分の試行を参照します。GETは試行を作成せず、有効期限を延長せず、コードを再送信しません。発行済みコードの長さや再送時刻を含む方式のメタデータを保持します。期限切れ、成功後の不可分な消費、キャンセル、Authのクリーンアップで継続は無効になります。明示的なログアウトと、その後の第2要素不要のログイン成功でも一致する試行を破棄します。

新しい保留中のログインは、要求Cookieが指す試行を置き換えます。タブはブラウザーのCookieを共有しますが、キャンセルでは表示中の試行IDを送るため、古いタブが新しい試行を取り消すことはありません。GETとDELETEは期限切れ後もCookieを上書きしません。共通Cookieのない同時の初回要求は独立した試行を作成し、ブラウザーが保持した応答Cookieが次の継続を選びます。どちらの要求も別のアカウントにセッションを与えません。完了済みのログインはキャンセルで取り消せません。試行はプロセス内に保持され、再起動で失われます。

SSO連携は `tfaRequired: true` を認証未完了として扱い、成功応答に明示された `loginUrl: "/login"` のみに従います。この印はAuthが有効な試行を一致するアカウントとプロバイダーに結び付けた後にだけ返します。Auth 2.2.10とX SSO 1.0.63を一緒に導入してください。古いホストがこの契約を提供できない場合、モジュールは継続を拒否します。ローカルログインとTFAなしのSSOは既存の完了経路を維持します。試行IDはメモリーまたは要求本文だけで扱い、URLやブラウザーストレージに保存しません。ログイン連携には現在の試行とフォームに限定された照会専用のルートが渡され、遅れて完了した処理が置換済みの画面を変更することを防ぎます。

## 有効期限付きチャレンジ配送

`auth:getPendingLoginLifetime` バージョン1は一次認証済みの既存試行から `{ id, accountId, expiresAt, signal }` を読むだけの公開契約です。権限の作成や延長はできません。Authは自動的な要素準備より前に試行を作りますが、セッション発行やプロフィール有効化はしません。不変の5分期限が配送にも適用されます。消費、中止、期限切れ、継続の置換、ログアウト、所有者の後処理でチャレンジ資源を中止します。Cookieに結び付いた継続、古い試行の保護、再配送なしの再開は維持します。要素検証の成功でチャレンジを終了しても、別の最終セッション確定は中止しません。この契約がなければTFAは処理を拒否します。

## アカウント対象の認可

別アカウントの管理、および対象を指定できるすべての TFA 読み取り、回復コード操作、方式の優先設定、有効化と無効化、管理者リセットには、Auth の `auth:authorizeAccountTarget` v1 ポリシーが必要です。管理者は他の管理者、所有者、創設者である管理者を管理できません。所有者に許可された操作は引き続き利用できます。ポリシーがない場合やアカウント情報を取得できない場合は、後続のストレージ操作前に拒否します。ユーザー管理の自己管理禁止は維持されます。TFA は対象の省略または自分自身の厳密な指定を受け付けます。設定と方式の詳細は本人専用のままです。空、重複、不正な対象パラメーターは拒否します。自分自身のセキュリティには設定を、管理可能な別アカウントにはユーザー管理を使用してください。

## パスワードフォームの文言

セキュリティは共有 XML キー `ui.reuse.password_requirements` と `ui.reuse.passwords_match` を使用します。登録済みの設定セクションは Auth とホストのカタログを読み込み、Registration の有効化を必要としません。パスワードポリシー、確認検証、プロバイダー制限は変更しません。Auth 2.2.13 と対応するホスト UI カタログを合わせて配置してください。
