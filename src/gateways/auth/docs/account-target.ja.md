# アカウント対象ポリシー

Auth は、アカウント管理と二要素認証管理で使用する特権アカウントの権限境界を管理します。

## 使用例

`system:contracts` を通じて `auth:authorizeAccountTarget` バージョン 1 を解決します。注入された Auth ガードの検証済みクレームを使い、`{ actor: { sub, role }, accountId, allowSelf }` を渡します。ユーザー管理は `allowSelf: false`、本人向け操作は `true` を指定します。

許可結果は `{ allowed: true, accountId, isCurrent }` です。返された対象が完全に一致することを確認し、使用直前に `isCurrent()` を呼びます。拒否結果は `{ allowed: false, status, code }` です。契約の欠落や非互換は利用不可を意味し、弱い検査への切り替えを許可しません。

省略可能な `allowFounder` 制約は、省略時に `true` として扱います。`false` を指定すると、実行者や対象のロールにかかわらず、創設者を `403 protected_founder_account` で拒否します。指定値が真偽値でなければ `400 bad_request` です。通常の Users 操作と TFA は既存の創設者の扱いを維持し、ガード付き登録解除だけがこの追加制約を要求します。代替プロバイダーもバージョン 1 契約の一部としてこの制約を実装する必要があり、黙って無視してはいけません。

`allowSelf: true` と `allowFounder: false` を組み合わせた場合、本人操作でも正式なメタデータを読み、創設者、存在しないアカウント、利用できないメタデータを拒否します。創設者制約を省略すれば、メタデータを読まない本人操作を維持します。

## 技術仕様

### 本人情報と権限

実行者の検証済み Auth クレームを引き続き権限の根拠とし、実行者のロールを再取得したり昇格させたりしません。通常のアカウントは、本人向け操作が許可されている場合に自分自身だけを操作できます。管理者は他のユーザー、教師、モデレーターのアカウントを管理できます。他の管理者または所有者を管理できるのは所有者だけです。保存されたロールが管理者または所有者の創設者は、実効ロールが所有者になります。創設者フラグだけでは他のロールは昇格しません。ユーザー管理固有の創設者、ロール、削除に関する追加制約は維持されます。

対象 ID は空でない未変更の識別子で、空白、制御文字、パス区切りを含めません。別アカウントへの要求は `auth:accountStore.getInfo(accountId)` を読み、一致する `accountId`、既知のロール、真偽値の `isFounder` を必要とします。存在しないアカウントは `404 not_found`、不正なメタデータ、読み取り失敗、提供元の利用不可は `503 account_policy_unavailable` になります。代替ロールや対象認可のキャッシュはありません。不正な要求は `400 bad_request`、アクセス拒否は `403 forbidden`、`protected_self_account`、または `protected_admin_account` を返します。

### ステージと有効期間

Auth は自身のブートストラップ有効期間内に、`validateRequest`、`readAccount`、`authorizeTarget` の各ステージを持つ `auth:authorizeAccountTarget` を登録します。入力はコピーして凍結します。非公開の操作状態により各ステージを一回の呼び出しに結び付けるため、フローの直接実行、取得済み入力の再実行、公開フローデータの変更では権限を得られません。許可された別アカウントの対象は拡張可能なステージの後に再取得し、遅延したフックが以前の低いロールや削除済み対象を保持することを防ぎます。

契約の削除、ブートストラップ失敗、無効化と再有効化、アカウントストアの置換は、保留中の処理と返却済みの有効期間チェックを無効にします。利用側も後続処理の前に、ルートの有効期間、現在の検証済み実行者、契約の登録そのものを再確認します。独立した要求間でメタデータの Promise や認可結果を共有しません。

これはある時点での認可チェックであり、アカウント情報と別コンポーネントのストレージにまたがるトランザクションではありません。最終読み取り後の変更はロックされず、`isCurrent()` は有効期間を検査するだけでロールを再取得しません。結果はすぐに使用し、後の操作用に保持してはいけません。

### 管理操作の準備と登録解除の変更処理

Users は検証済みの実行者を一度コピーして凍結します。本文やメタデータの準備より前の拒否を維持し、それらの待機後、最初の変更直前にポリシーを再取得します。許可されたロール変更の開始後は、同じ実行者とライフサイクルの検査でプロフィール同期を保護します。操作自身が設定した管理者ロールを対象に再認可すると、正当な昇格が途中で止まるためです。

HTTP の `deprovision-user` 入力には、凍結した `actor` と副作用のない `isAuthorizationCurrent()` 関数も渡します。Auth は `authorize-request` でこれらを内部に保存し、関数を厳密に検査し、拡張可能な準備段階の後の `persist-state` でバージョン 1 の対象ポリシーを再取得します。指定されたガードが空、不正、例外を発生、または厳密に `true` を返さない場合は拒否します。後続の入力やステージ結果の変更で保存したガードを削除することはできません。最終ポリシーの拒否は `persisted: false`、`status`、`reason` を返し、Users は成功ではなく対応する応答を一度だけ送ります。

既存の LDAP 同期は HTTP 実行者とガードを省略する別のシステム所有者ワークフローです。Users の代替経路ではありません。削除と無効化はアカウントストアの変更から始まり、アーカイブは `persist-state` 内のセッション失効から始まります。後処理は保存済みの失効件数を報告し、失効を繰り返しません。変更開始後は権限の有効期間が終了しても既存の依存関係の後処理を完了でき、後続のプロフィール変更前にはルートが実行者とライフサイクルを再検査します。ストアをまたぐトランザクションではないため、開始済みの外部処理をこの検査で中止したりロールバックしたりすることはできず、一部だけ完了する可能性があります。ガード付き登録解除は `allowFounder: false` を渡し、最終ポリシーが現在の創設者フラグと対象ロールをまとめて評価します。所有者が開始した操作を含め、すべての創設者ロールに対する既存の禁止を維持します。この時点検査の対象外となるのは、その最終読み取りより後の変更だけです。

### 正式な登録解除結果

`auth:deprovisionOutcome` バージョン 1 は Auth 所有のオブジェクト契約で、`read(input, stageResults)` と `deletedAccount(input, stageResults)` を提供します。実際のフロー実行で使った元の入力オブジェクトと、その呼び出しの結果マップの同一性を検査します。コピー、別の呼び出しとの組み合わせ、未完了の操作には証明がありません。入力オブジェクトを再使用すると新しい呼び出しになり、以前の証明は無効になります。返す結果は凍結され、後続フックが公開ステージ結果を置き換えたり入力フィールドを変更したりしても、所有者の非公開状態が正式な結果です。

`read` は所有者の最終結果 `{ persisted: true, username, action, revokedTokenCount? }` または `{ persisted: false, status, reason }` を返し、利用できなければ `undefined` を返します。`deletedAccount` は削除が実行済みの場合だけ保存済みのアカウント ID を返します。両メソッド自身が Auth 世代、契約宣言、プロバイダー同一性を検査し、無効化と再有効化や置換後の保持済み参照も拒否します。結果証明はロールを再読込せず、開始済みの変更を取り消しません。

Users はフロー開始前にリーダーを固定し、返された対象と操作を検査し、応答と後続プロフィール変更には所有者の結果だけを使います。Auth アカウントインスタンス、Calendar、Keyring、Profile、Classes、Messages、Internal Notification の後処理は `ctx` 経由で `deletedAccount` を解決します。公開 `persist-state` 値や変更可能な入力フィールドは削除を許可できません。結果プロバイダーが欠落、不適合、不正な場合は拒否します。Auth と更新済みの利用側を一緒に配置してください。代替プロバイダーもこの呼び出し同一性契約を実装する必要があり、公開結果だけを読む旧利用側はこの保護に対応しません。既存の後処理順序と開始済み処理の一部完了の制限は変わりません。

既知の外部モジュールの境界：[Jitsi リビジョン 2dfe50b](https://github.com/Cognis-Labs-HQ/cognis-module-jitsi-meet/blob/2dfe50bfd46f32e08291a2aacbdeb27d559fb2f8/api/index.js#L380-L451) は会議と関連リソースの後処理に公開された永続化結果と入力フィールドを使っています。導入環境が保護されたと扱う前に、`auth:deprovisionOutcome` へ移行するか無効化する必要があります。同梱側の変更だけでは古い外部フックを保護できません。製品 API と起動処理の読み取り専用ソース監査では、Whiteboard `ef9e9b4` と Terms `330bf49` に該当する後処理利用側はありませんでした。これはソース監査の結果であり、実行済みの互換性テストではありません。

Auth は Core 0.6.6 で実装された、フロー実行コンテキストの浅い不変性を必要とします。この Core を Auth と結果証明の利用側より先に、または同時に導入してください。実行時にはバージョン名ではなく実際に凍結されたコンテキストを検査します。未凍結の旧ランナーでは対象メタデータや登録解除の変更処理より前に利用不可となり、その検出によって以前の判断と結果証明も無効になります。検証済み依存バージョンの上限だけでは、この最低条件を保証できません。不変なのはコンテキストの参照だけで、入力、data、結果の内部は変更できるため、所有者の正式な結果証明は引き続き必要です。拡張はトップレベルのコンテキスト参照を置き換えず、共有処理には変更可能な data フィールドを使ってください。

### 統合

Auth 2.2.12、TFA 1.3.13、API 0.13.36 を合わせて配置してください。古い Auth や代替実装は、別アカウントの管理を利用可能にする前に、実行可能なバージョン付き契約を提供する必要があります。ストアの直接参照や呼び出し側の最低ロール検査への切り替えはありません。本人向け TFA 設定、方式の詳細、保留中ログインの操作は、クエリパラメーターによって別アカウントを対象にしません。
